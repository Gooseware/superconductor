# Specification: Regression Protocol: Capability Invariant Ledger

## Overview
Superconductor currently lacks memory of what critical capabilities should always exist. A regression reviewer only inspects `git diff main..HEAD`, which cannot detect features deleted in a prior track that were already missing from `main`. This track adds a **Capability Invariant Ledger** to provide cross-track regression detection capabilities.

## Architecture & Design

### 1. New Note Type: `invariant`
Written to the Superconductor Notebook (LanceDB/FTS5 in `packages/notebook-store/`) when a track creates a durable capability.
**Fields:**
- `type`: "invariant"
- `capability`: human-readable name (e.g. "/superconductor:implement")
- `path`: filesystem path or glob that must exist (e.g. "commands/superconductor/implement.toml")
- `rationale`: why this capability exists and why it matters
- `track`: track_id that created it
- `created_at`: ISO timestamp
- `removable_if`: the condition that would legitimately justify removing this capability

### 2. New Note Type: `invariant_override`
Written by a track that intentionally removes a capability.
**Fields:**
- `type`: "invariant_override"
- `capability`: name of the invariant being overridden
- `justification`: why it's being removed
- `track`: track_id doing the removal

### 3. Regression Reviewer Enhancement
The regression reviewer agent gets a new pre-check step that runs BEFORE the git diff analysis:
1. Query notebook: `notebook_query({ note_types: ['invariant'], limit: 200 })`
2. For each invariant: check if the specified path/glob exists on disk.
3. If missing: check if THIS track has a matching `invariant_override` note.
4. If missing with no valid override, raise CRITICAL finding: 
   `REG-INV-N: Capability '<name>' no longer exists. Rationale: <why it matters>. To intentionally remove: write an invariant_override note satisfying: <removable_if>.`

### 4. Invariant Write Protocol
Added to the `implement` skill (Phase 4 / Finalization step).
- Processor must ask: "Did this track create any durable user-facing capabilities, APIs, entry points, or infrastructure that should never silently disappear?"
- If yes, write `invariant` notes for each via `notebook_write`.

### 5. Bootstrapping
A bootstrap task must write invariant notes for all existing known capabilities:
- `commands/superconductor/*.toml` slash commands
- MCP tools registered in `superconductor-kernel`
- Skills in `skills/` directory
- Key orchestration files (WorkspaceGuard, SignOffGate, QuorumFSM)

### 6. Human-Readable Invariants File
A flat `superconductor/invariants.md` must be generated and maintained as a human-readable mirror of the notebook invariants. It acts as an audit trail (auto-generated by a script), but the notebook remains the source of truth.

## Acceptance Criteria

- [ ] **Notebook Schema:** `invariant` and `invariant_override` note types are supported in `notebook_write` and filterable in `notebook_query`.
- [ ] **Regression Reviewer:** The reviewer agent (`regression-reviewer/agent.md`) includes the new pre-check step validating invariants and emitting the `REG-INV-N` finding if broken without override.
- [ ] **Implement Protocol:** `skills/implement/SKILL.md` instructs the processor to ask about and write durable invariants during finalization.
- [ ] **Bootstrapping:** All known capabilities (slash commands, kernel tools, skills, orchestration files) have corresponding `invariant` notes in the notebook.
- [ ] **Audit Trail:** A script successfully generates `superconductor/invariants.md`, reflecting all current invariants in the notebook.
